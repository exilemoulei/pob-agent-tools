# Architecture

How pob4agents is built and the contracts it keeps. Read this before changing code; [AGENTS.md](../AGENTS.md) has the commands and the short rules. When this doc and the code disagree, the code wins and this doc gets fixed in the same change.

## How a command runs

```text
pob <command>  (L4 cli*.py, lazy-loaded subcommands; `_lua-host` pre-dispatched before Click)
  -> daemon on 127.0.0.1, HTTP/JSON with X-PoB-Token  (L3 daemon/)
    -> BridgeWorker, NDJSON over stdin/stdout  (L1 bridge_client.py, advertises `version.caps`)
      -> Windows (slim ~45 MiB engine, zero pob-zh.exe): `pob _lua-host` (ctypes `PoE1/lua51.dll`) running `lua/headless_runner.lua` + `win32_ffi.lua` (falls back to `pob-zh.exe` only for read-only legacy PobTools seeds lacking `lua51.dll`)
         macOS / Linux: LuaJIT 2.1 + lua-utf8 running the same `lua/headless_runner.lua`, which boots PoB with lazy hooks, hybrid PRNG+mmap Timeless LUTs, CoW snapshots, direct calc, and agent probes, then loads PobTools-zh's `bridge.lua`
```

- The CLI starts the daemon in the background on first use (the frozen `pob.exe` through a hidden `pob _daemon` command), or `pob serve` runs it in the foreground. The daemon writes `daemon.json` (`pid`, `port`, `token`) and keeps one engine worker per named build slot (`--target <slug>`, default `POB_SLOT` or `main`).
- What-if commands use in-memory shallow Lua CoW snapshots (`cow_snapshot`/`cow_restore`) and single-pass `direct_calc` when the worker advertises `caps.cowSnapshot`/`caps.directCalc`, falling back to `export_code`/`import_code` rollback (`snapshot/`) for legacy hosts and `FakeWorker` tests. A CoW snapshot covers only the active tree spec and item/skill/config sets of the build it was taken from, so mutations that switch or add a set, spec or loadout, or replace the build, take an `export_code` checkpoint instead; Lua refuses a stale snapshot (and keeps at most 16), and a failed `cow_restore` re-imports the saved build code and reports `restoreFallback`. `--apply` keeps the change and pushes a lossless share code onto the undo stack.
- `pob data` and `pob ground` do not need the daemon: they query a SQLite index built from the engine's Lua data (`game_data/`).

## Modules and layers

`pob_cli/src/pob_cli/` is a strict five-layer DAG: a module imports from its own layer or below, never above, and there are no import cycles. `pob_cli/scripts/arch_lint.py` (`LAYER_MAP`) enforces it, together with the size budgets: every file at most 650 lines and 24,000 bytes, every function at most 200 lines.

| Layer | Modules | Role |
|---|---|---|
| L0 | `errors.py`, `ticks.py`, `os_util.py`, `compat.py`, `json_io.py`, `guardrails/` (incl. `redact.py`, `reply_patterns.py`, `reply_scanner.py`) | Foundation and static rules: error types, tick math, process/lockfile helpers, signature-compat/UTF-8 helpers, fail-safe JSON I/O, secret redaction, PoE2 guardrails, reply scanning for hooks |

| L2 | `formatters/`, `snapshot.py`, `analyzer/`, `mutators/`, `comparator/`, `bench/`, `item_inspect.py`, `trade_craft.py`, `trade_item/`, `trade_client/`, `trade_query/`, `trade_eval/`, `timeless/` | Domain core: rendering, what-if transactions, audits, build edits, comparison, crafting bench, trade, timeless jewels |
| L3 | `daemon/` | The daemon server and its client |

Bundled with the package: `data/bench_costs.json` (generated by `pob_cli/scripts/update_bench_costs.py`), `data/timeless_meta_3_30.lua.gz` (`3.74 KiB` PRNG metadata generated by `pob_cli/scripts/update_timeless_meta.py`), and every `lua/*.lua` (`pob.spec` globs them: `headless_runner.lua`, `import_char_json.lua`, `zh_translate.lua` (with `zh_json.lua`), `zh_reverse.lua`, `win32_ffi.lua`, `lazy_hooks.lua`, `timeless_prng.lua`, `timeless_mmap.lua`, `fast_calc_cow.lua` (which loads `fast_calc_direct.lua` beside it), `upstream_kernels.lua`, `agent_probes.lua`). Outside the package: the cross-harness agent skill `skills/pob/SKILL.md` (with `references/`) and the hook configs `hooks/hooks.json` (Antigravity) and `hooks/claude-hooks.json` (Claude Code).

## Engine and paths

Engine lookup (`updater.resolve_engine_root`):

1. `POB_ROOT`, if it is a valid engine.
2. `<POB_RUNTIME_DIR>/engine`. The default runtime dir is `<repo>/.runtime` in a source checkout, `%LOCALAPPDATA%\pob4agents` for an installed or frozen Windows build (falling back to a legacy `%LOCALAPPDATA%\pob-agent-tools` that already has runtime data), and `${XDG_DATA_HOME:-~/.local/share}/pob4agents` on macOS and Linux.
3. A read-only legacy seed: `POB_LEGACY_DIR` or `<repo>/PobTools[20261102]`. Never write to it. In PowerShell always pass that path with `-LiteralPath` (the brackets are wildcards), and the engine's working directory must be its `PoE1` folder.

`pob bootstrap` installs a slim managed engine (`~45 MiB` on Windows, zero `pob-zh.exe`, zero bulky images/fonts/legacy trees/`.zip*` Timeless LUT blobs): it downloads only PoB's runtime core + `PoE1/lua51.dll` & `zlib1.dll`, extracts only `Data/bridge/`, `Data/poe1/zh-rCN/` and `Data/poe1/zh-rTW/` from PobTools-zh (or seeds offline with `--from-dir`), and runs PoB via the native LuaJIT host (`updater/win_lua_host.py` on Windows, `engine/bin/luajit` on POSIX). Timeless jewels (`1..6` Legion/Heroic + `7..11` 3.30 Abyss) default to on-the-fly PRNG synthesis (`lua/timeless_prng.lua` + `3.74 KiB` `data/timeless_meta_3_30.lua.gz`), with automatic on-demand `.zip*` + `lua/timeless_mmap.lua` fallback for future jewel types, tree mismatches or a PoB whose addition count differs from the metadata's; fetched tables are cached under the SHA-1 of the installed `NodeIndexMapping.lua` and fetched only from a PoB with that same mapping. A build on a tree version the slim engine leaves out gets that version's `TreeData/<ver>/` files fetched before `import_code`: a version counts as installed only when every file `manifest.xml` lists for it is present and SHA-1 checked (newline-tolerant), the files are staged and renamed into place only once all of them verified, all versions share a 12 s budget, and a version that cannot be fetched (offline, network failure, retried within a minute) stops the import with a clean `Error:` that says to run pob online. `pob update` applies incremental SHA1-checked slim updates (`ETag 304`) and hot-reloads live daemon slots. Updates run a `gate_result` smoke probe and roll back from `.bak/` when it fails.

pob updates itself separately (`updater/self_update.py`, `cli_self_update.py`). On an interactive terminal, a command ends with a stderr line when a newer release exists; it reads `<POB_RUNTIME_DIR>/pob_release_check.json`, which a detached `pob _release-check` refreshes at most once a day from the `/releases/latest` redirect, so no command waits on the network for it (off for `hook`, `serve`, `--offline`, `POB_OFFLINE=1` and `POB_NO_UPDATE_NOTICE=1`). `pob self-update` replaces a standalone build in place after the release's signed `SHA256SUMS.txt` and the build's SHA-256 verify and the new build runs: on macOS and Linux by swapping the build directory, on Windows through a detached PowerShell step that swaps it once no process started from the install folder (the CLI and the daemon) still runs, retrying the move with backoff and writing `<app>.swap-result.json` next to the folder; the next `pob` run reports a swap that failed. Windows refuses to start when the current directory is inside the install folder. One update runs at a time (an exclusive `<app>.update.lock` next to the folder), each in its own `<app>.update-*` staging folder that is removed on failure, and a network, disk or swap failure exits `5` with a clean `Error: ...`. A damaged notice cache counts as never checked, and the notice never fails the command it follows. Scoop, uv, pipx, pip and source installs get their own update command instead (`pob self-update --check` prints it).

On macOS and Linux, bootstrap also installs `engine/bin/luajit` and `engine/bin/lua-utf8.so` (`updater/posix_runtime.py`), taking the first that works: the copy inside a standalone build (`_internal/runtime/bin`); `pob4agents-runtime-<version>-<platform>.tar.gz` from this pob's release, then the latest one, trusted only through that release's signed `SHA256SUMS.txt`; or a local compile of LuaJIT and lua-utf8 from source tarballs pinned by SHA-256 (`constants.py`, and `build_posix_runtime.sh`, which a test keeps equal). Each candidate must pass a self-test (`+=`, `..=`, `require("lua-utf8")`) first. pob before 0.9 asked for `pob-runtime-<platform>.tar.gz` without any check; no release publishes that name, so those versions keep compiling.

Runtime state in `<POB_RUNTIME_DIR>/`: `config.json` (the language `pob lang` saved), `daemon.json`, `update_state.json`, `slot_<slug>.json`, `turn_receipts.jsonl`, `hook_turn_<hash>.json`, and a shared `cache/` with `gamedata_<pobVer>_<dataVer>.sqlite` (`..._zh_rtw.sqlite` for zh-TW), `ninja_*.json`, `poedb_*.json`, `trade_ratelimit.json` and `trade_stats*.json`. A rebuilt `gamedata_*` or `treedata_*` index deletes the superseded ones, keeping the newest other file for a second engine that shares the cache.

## Chinese locales

The display language is `zh-CN` (Simplified, `Data/poe1/zh-rCN`) by default, or `zh-TW` (Traditional, `zh-rTW`) or `en`, chosen by `POB_LANG`, then `<POB_RUNTIME_DIR>/config.json` (written by `pob lang`), then the default (`locale_cfg.py`). `pob lang <lang>` refuses a locale whose folder the engine lacks, saves it, and switches running daemon slots live through `lua/zh_translate.lua`'s `set_locale`; an explicit switch also replaces a `POB_LANG` the daemon inherited at start. The legacy `pob-zh.exe` has no `set_locale`, so it can only turn Chinese on or off, not pick zh-CN or zh-TW (`legacyFallback` in `pob lang --json`).

zh-rCN ships fewer tables than zh-rTW (no affixes, title words, gem or ascendancy ids, GGPK display text). Under zh-CN, `zh_translate.lua` borrows zh-rTW's tables for keys zh-rCN lacks and folds them to Simplified with the `tables_han.py` / `tables_tw.py` maps, so magic affixes and rare titles carry zh-rTW's wording in Simplified characters. `pob.spec` bundles both tables as data files so frozen builds can read them too. `--json` output keeps engine warnings in English (`raw`); the localized text stays in the human output.

Queries and slang are mostly Simplified, the display may be either script, and the two translations often word the same thing differently (Mageblood is 法师之血 in zh-rCN and 魔血 in zh-rTW). Worse, a Simplified name can fold onto a different zh-rTW entity (术士手套 is Sorcerer Gloves, 術士手套 is Warlock Gloves). So:

- `english_for_zh` and `pob data translate` try an exact, unfolded match in both dictionaries before any folded match, zh-rCN first when the query is already Simplified (`query == fold_han(query)`), zh-rTW first otherwise, whatever the display language. CN-server imports (`profile_import/cn_zh2en.py`) always load zh-rCN first.
- The game-data index reads only name tables: zh-rTW's id-keyed files (`*_by_id.json`), `ggpk_*` dumps and lookup configs (`synonyms.json`, `display_exclude.json`, ...) stay out, as do keys that are digits or snake_case stat ids.
- Both sides are folded to Simplified with `game_data.fold_han` (mutator search folds, `analyzer/calcs.py`, class and ascendancy, item DB, gems).
- A Chinese entity name that still finds nothing is retried by its English name from `game_data.english_for_zh`, because the engine always carries the English name.
- The local index folds the same way: `game_data._fold_search_text` builds every `*_lower` column and folds every `pob data`, `pob ground` and `--slot` query, and `pob bench` search and trade stat names fold too, so 圖騰 finds 图腾. Fold both sides, never the query alone: Simplified text keeps a few foldable characters (覆盖 would turn into 复盖 and miss). A change to the fold bumps `SCHEMA_VERSION` and `TREE_SCHEMA_VERSION`, which rebuilds the index.
- Equipment slot names fold at the caller. The slot aliases live in `guardrails/` (L0), which cannot import `fold_han` (L1), so `analyzer.resolve_slot_name`, the mutators' slot lookup, `bench.slot_key` and turn receipts fold before they call `normalize_equipment_slot`; a new caller must do the same. The reply scanner stays in L0 and only knows the slot words spelled out in its own tables.

`game_data/tables_han.py` is generated from Unicode's Unihan data by `pob_cli/scripts/gen_han_fold.py <Unihan.zip>`; hand-picked PoE terms in `tw_norm.py` override it.

## Hard constraints (`R1`..`R13`)

### Engine RPCs

`arch_lint.py` (`[blocked-rpc]`) rejects these outside `bridge_client.py` / `bridge_protocol.py`:

- `R1` `compare_*`: compare builds with two slots through `comparator/`.
- `R2` `sidebar_breakdown`: allowed only when the runtime reports `caps.sidebarBreakdown == True`; otherwise use `get_calcs` + `calcs_breakdown`.
- `R3` `config_mod_search` / `config_mod_add`: use `list_config` / `set_config` / `set_custom_mods`.
- `R4` `set_pob_options` / `oauth_logout`: never change PoB's `Settings.xml`; every boot starts with `new_build{}`.
- `R7` `import_from_uri`: it rejects non-ASCII and parentheses; import through `importers.py`.
- `R11` `save_build_as`: the CLI writes files to disk itself.

### Numbers

- `R5`: every DPS, EHP and other build number comes from the headless engine. Never estimate one in Python or read one out of build XML.

### Reliability (`R8`..`R12`)

- `R8`: `BridgeWorker` uses an `RLock`, drains `stderr`, heals the `import_code` `b:Shutdown()` deadlock (`new_build{}`, then restore `last_good_code`) and flags `treeVersion` mismatches.
- `R9`: colour codes (`^xRRGGBB`, `^0`..`^9`) are stripped only in `formatters/`, keeping the raw keys.
- `R10`: the daemon listens on `127.0.0.1` only and requires `X-PoB-Token`.
- `R12`: `tree_click` checks `allocatedNodes` before every click; anoints validate against `notableDB` first.
- Dewatering disables `customMods` per group in place (`enabled=False`) and appends the sentinel `{"title":"pob-cli dewater","text":"# disabled","enabled":True}`; it re-applies `presetBossSkills` after `enemyIsBoss`, defaults Vaal gems to `enableGlobal1=False` (Vaal burst) and `enableGlobal2=True` (base skill), and proves read-only rollback with `verify_restored`.

### Engine and updater red lines

- Never commit the 1 GB `PobTools` pack (its `Data/` dictionaries are not MIT, and its font has no redistribution licence).
- Never run stock LuaJIT on PoB >= 2.68: PoB uses `+=` / `..=`, which only PobTools' host and the runtime from `packaging/build_posix_runtime.sh` (LuaJIT at PathOfBuilding-SimpleGraphic's commit) accept.
- Never call `api.github.com`; find the latest tag from the `302 Location` of `releases/latest`.
- Never call PoB's `UpdateCheck.lua` / `UpdateApply.lua` inside a worker.
- Update checks fail fast (`connect=3s`, `read=8s`). On `degraded_*` the CLI prints one Chinese alert to `stderr`, and `status` / `summary` / `load` expose a top-level `updateWarning` (JSON) and `> [WARN]` (Markdown). If `pob load` fails while degraded, the answer is a proxy and `pob update --proxy ...`, never blaming the build or parsing XML by hand.

### External APIs (`R6`, `R7`)

- Public international official profiles (`www.pathofexile.com/account/view-profile/...` -> `character-window/get-*`) are queried with `Path of Building` User-Agent and no cookies (falling back to env `POESESSID`/`POE_COOKIE` only on 401/403 private profiles); both international and CN character JSON bundles use capability-based dispatch: `lua/import_char_json.lua` (`import_character_json` RPC) when the worker advertises `importCharacterJson`, otherwise pure-Python PoB XML (`profile_import/pob_xml.py`) + `import_code`.
- CN server profiles (`poe.game.qq.com`) use `POST` form requests with env `POE_CN_SESSID`/`POE_CN_COOKIE`, pure-Python ZH->EN translation against local `PobTools-zh` `Data/poe1/zh-rCN/` dictionaries (`profile_import/cn_zh2en.py`), and surface any unmatched Chinese mod lines as `[CN-TRANSLATE-WARN]`.
- Never bypass Cloudflare Turnstile on `poe.ninja/poe1/builds/*` HTML. poe.ninja character import tries the `Name-1234` hyphen form first (the `#` form only after a 404) and resolves `overview` from `build-index-state` / `index-state`.

### Trade and bench (`R13`)

- Read-only official PoE1 trade API: no whispers, no buying, no game input.
- `POESESSID` / `POE_COOKIE` come from the environment only, after a 401/403; never log, print or pass them as arguments (they are redacted).
- Honour GGG's dynamic `X-Rate-Limit-*` headers and `Retry-After`; treat listing text as untrusted data.
- Harvest swaps (`--allow-conversion`) apply only to identified rare or magic explicit single-element mods (never unique, corrupted, mirrored, crafted, fractured, implicit, enchant, or a same-group conflict) and always carry the `rerolled: true` caveat.
- DPS/EHP only from PoB: `-` means unverified, never a `0` upgrade.
- Exit codes: `0` ok, `1` argument or stat, `2` no results, `3` cookie / Cloudflare, `4` rate limit, `5` API error, `6` `--pob on` failed.

### Exit-code contract

`DaemonRequestError` / `ValueError` (`errorKind: "request"`) exit `1`; a daemon, engine or transport fault (`errorKind: "daemon"`) exits `5` with a clean `Error: ...` and no traceback; trade follows `R13`.

### PoE1 only

`guardrails/` blocks PoE2 input with exit `1` and `errorKind: "cross_game_hallucination"`, and redirects to the `pob` equivalent or the `pob2` CLI:

- PoE2 builds (`<PathOfBuilding2>`, `treeVersion="0_*"`, PoE2 classes, `Charm 1..3`), PoE2-only engine roots, `daemon.json` with `game == "poe2"` (non-destructive), and `X-PoB2-Token`.
- PoE2 URLs: `poe2db.tw`, `/trade2/`, `poe.ninja/poe2`, `poe2wiki.net`, `maxroll.gg/poe2`, `mobalytics.gg/poe-2`, `pob2://`.
- PoE2 terms (Table D): `Uncut *`, `Distilled *` / 涂灌, `Waystone` / 引路石, `Soul Core` / `{rune}`, `--slot focus` / `quarterstaff` / `charm1`, `Spirit` / 精魂.
- CLI traps: `pob rune`, `pob instill`, `pob item charm`, `pob item instill`.

It never blocks PoE1-legal terms: `Elemental Focus`, `Combat Focus`, `while Focused` / 专注, `Titanium Spirit Shield` / 灵盾, `Summon Raging Spirit`, `Spirit Offering`, `Distilled Perfection`, `Ancient Waystones`, and, outside `SLOT` / `CATEGORY`, the level 45 staff base `Quarterstaff` and the `Buckler` shield bases (`Crusader Buckler`).

## Adding a command

1. **Put the logic in L2** (`analyzer/`, `mutators/`, `comparator/` and so on), on fakes first. Numbers come from the engine, never from a formula of our own (see "Numbers").
2. **Reach the engine through the daemon.** A new engine call is a handler in `daemon/rpc_handlers.py` (or `rpc_mutate.py` for edits) that calls the engine through its `BridgeWorker`, never with an RPC from "Engine RPCs" above. A what-if snapshots and rolls back (`snapshot.py`) unless `--apply` is given.
3. **Add the CLI in L4.** Register it from an existing `cli_*.py` through its `register_*_commands`, or, for a group with heavy imports, add a `cli_<name>` module to `_LAZY_SUBCOMMANDS` in `cli.py` and to the `hiddenimports` of `packaging/pob.spec`. Give a new top-level module its layer in `LAYER_MAP` (`scripts/arch_lint.py`).
4. **Keep the contracts**: exit codes (`1` for a bad request, `5` for a daemon or engine fault), Chinese names folded with `game_data.fold_han`, and PoE2 terms refused by `guardrails/` without blocking a PoE1 term.
5. **Test** offline on fakes. A command that reaches the engine also gets a real-engine test that skips without an engine; a new real-engine test raises the ratchets in `engine.yml` in the same change.
6. **Document** every flag in `docs/guides/commands.md` and both READMEs, and the recipe in `skills/pob/SKILL.md` (or its `references/`) when agents should use it.

## Verification

- `python pob_cli/scripts/check.py --fast` (under 3 s): `ruff` on `src`, `scripts`, `packaging` and `tests`, plus the AST checks `[file-budget]`, `[fn-budget]`, `[layer-dag]`, `[blocked-rpc]` and `[spec-sync]` (every lazy subcommand module exists and is bundled by `packaging/pob.spec`).
- `python pob_cli/scripts/check.py --self-test`: five mutation checks in a temp dir proving each rule fires.
- `python pob_cli/scripts/check.py`: the fast gate plus isolated `pytest`, with a ratchet on passed and skipped tests (`--min-passed N --max-skipped N`). Without those flags the skip budget follows what the machine can actually run: 25 with the legacy PobTools seed, 32 with a bootstrapped slim engine (Windows keeps its POSIX-only and slim LUT skips), 65 with no engine at all, which prints a line saying so. `engine.yml` always passes explicit counts, so CI keeps an exact ratchet.
- Real-engine tests find an engine through `POB_ROOT`, `<repo>/.runtime/engine`, then `<repo>/PobTools[20261102]` (`pob_cli/tests/engine_paths.py`) and skip when there is none.

## CI and releases

- `ci.yml` (pull requests and `main`): lint and architecture gate; engine-less tests on Windows, Linux (Python 3.11 floor and 3.14) and macOS; the Windows package build with a no-engine smoke test; the POSIX LuaJIT runtime build; `install.ps1 -SelfTest` on PowerShell 7 and 5.1. The `install.sh` tests (`test_install_sh.py`) run it end to end against a fake signed release on localhost.
- `engine.yml`: bootstraps a fresh engine and runs the full gate on Windows, Linux and macOS, plus the frozen `pob.exe` against the real engine on Windows. It runs nightly through `engine-nightly.yml` (which opens or comments on one tracking issue on failure), on `workflow_dispatch`, on pull requests that change it, and as the release gate.
- `release.yml` (pushing a `v*` tag): `prepare` checks the tag against `__version__` in `pob_cli/src/pob_cli/__init__.py` (the single source) and refuses an already published release; `gate` runs `engine.yml`; `build-python`, `build-windows` and `build-posix` build the wheel, the sdist and the PyInstaller builds without write access (macOS arm64 and x64 on `macos-15` / `macos-15-intel`; Linux x64 and arm64 inside a digest-pinned Debian 12 Python image, so they need glibc 2.36 or newer; each Linux and macOS build carries the LuaJIT runtime and passes `packaging/smoke_frozen.sh`); `assemble` writes `SHA256SUMS.txt` (a dry run also signs it with a throwaway key and checks the file set); `sign`, on tag runs only and in the `release` environment, signs it into `SHA256SUMS.txt.sig` and checks the exact file set and the signature against pob's public keys with `pob_cli/packaging/release_tools.py verify`; `publish` attests every file listed in `SHA256SUMS.txt` (`gh attestation verify <file> -R exilemoulei/pob4agents`), uploads to a draft, verifies the uploaded copies and publishes (prereleases never become "latest"); `installer` and `installer-posix` install the new tag with `install.ps1` and `install.sh`; after both pass, `scoop` opens and merges a PR that points `bucket/pob.json` at it (a rerun reuses the open PR and force-updates only its own `release/scoop-<tag>` branch); and `publish-pypi`, when `vars.ENABLE_PYPI` is set and the release is not a prerelease, publishes `pob4agents` and `pob-cli` to PyPI through trusted publishing (environment `pypi`; each project needs this workflow as its trusted publisher). A failed release is retried with "Re-run failed jobs", which reruns the failed jobs and the jobs after them: a failed build or `sign` is redone, a failed `publish` refreshes the draft, and `publish` stops rather than touch a release that is already published. Dispatching on a branch is a dry run of it (gate, build, verify, install the latest release; nothing uploaded), and pull requests that touch release inputs run the same dry run without the engine gate.
- Release environment (owner setup): `RELEASE_SIGNING_KEY` belongs in a GitHub environment named `release` (Settings > Environments) whose deployment rule allows only tags matching `v*`, and is removed from the repository secrets, so only the `sign` job of a tag run can read it. A tag ruleset (Settings > Rules) on `refs/tags/v*` restricts who may create, update or delete release tags. Until the environment exists, GitHub creates it on the first tag run without protection, and the job falls back to a repository secret of the same name.
- Asset names (`release_tools.py` is the one list): `pob4agents-<version>-<platform>.zip` (Windows) or `.tar.gz` (`macos-arm64`, `macos-x64`, `linux-x64`, `linux-arm64`), each with a version-free alias such as `pob4agents-windows-x64.zip` for `/releases/latest/download/`; `pob4agents-runtime-<version>-<platform>.tar.gz` for macOS and Linux; the `pob4agents-<version>` wheel and sdist (named `pob_cli-<version>` up to v0.8.0), whose names carry the PEP 440 form of the version that `python -m build` writes (`0.9.0-rc.1` becomes `0.9.0rc1`), while tags and standalone archives keep it as written. The distribution is `pob4agents` (it was `pob-cli`; the import package stays `pob_cli`), and `pob-cli` on PyPI is a code-free alias built by `release_tools.py shim` that only depends on `pob4agents==<version>`. It declares no scripts, so `pob` belongs to `pob4agents` alone (uninstalling `pob-cli` never removes it): `pip install pob-cli` gets `pob` through the dependency, while uv and pipx, which install only the named package's commands, need `pob4agents`. It is never attached to the GitHub release. Build jobs upload release files as `asset-*` artifacts, which is all `assemble` collects. Windows also keeps the names releases up to v0.8.0 used, `pob-v<version>-windows-x64.zip` and `pob-windows-x64.zip`, for saved scripts, pinned versions and README links. `install.ps1` picks whichever name the release's `SHA256SUMS.txt` lists.
- `install.sh` installs the standalone build into `${XDG_DATA_HOME:-~/.local/share}/pob4agents/bin` and links `~/.local/bin/pob` to it (removing an earlier uv or pipx install of `pob-cli`, which would shadow it). When the release has no build for the machine or the build does not run (an older glibc), it installs the release's wheel with uv, pipx or pip, or its sdist when there is no wheel, each checked against the signed `SHA256SUMS.txt`, and stops when the release lists neither; `POB_BRANCH` installs a branch or tag from source on purpose, and `POB_FROM_SOURCE=1` forces the wheel. The old build directory is swapped out only once the new one is in place and runs through the link; a failed swap puts the old one back and stops.
- Release signing: `SHA256SUMS.txt.sig` is the base64 Ed25519 signature of `SHA256SUMS.txt`'s exact bytes, made with OpenSSL from the `RELEASE_SIGNING_KEY` secret, which only the `sign` job of a tag run receives (dry runs sign with a throwaway key). The public keys live in `RELEASE_PUBLIC_KEYS` (`pob_cli/src/pob_cli/updater/signature.py`, a standard-library RFC 8032 verifier) `$ReleasePublicKeys` in `install.ps1` (a plain-PowerShell verifier; `install.ps1 -SelfTest` runs the RFC test vectors in CI on PowerShell 7 and 5.1) and `RELEASE_PUBLIC_KEYS` in `install.sh` (OpenSSL 3, or an embedded python3 verifier where OpenSSL cannot; `install.sh --self-test`); tests keep the three lists equal. Both installers accept only a `vX.Y.Z[-pre]` tag and refuse any release after v0.8.0 whose signature is missing or does not verify (a version that does not parse counts as one that needs a signature). Through a GitHub mirror (`POB_GITHUB_MIRROR`), which also picks the tag when none is pinned, every release needs a valid signature, so a mirror can serve files but not change them; releases from before signing install only straight from GitHub. When a release needs a signature and `install.sh` has no Ed25519 verifier (neither OpenSSL 3 nor a usable python3, as on a Mac without the Command Line Tools), it stops before downloading anything and names `xcode-select --install` or `brew install openssl@3`; `POB_SKIP_SIGNATURE=1` lets it go on with HTTPS from GitHub and SHA-256 alone, with a warning, and never applies through a mirror. To create or rotate the key, the owner runs `python pob_cli/packaging/release_tools.py keygen --out <file>` offline, stores the PEM text as the `RELEASE_SIGNING_KEY` secret, and adds the printed public key to all three lists in a commit that is released before the new key signs anything.
- `codeql.yml` (Python and Actions) runs on push, pull requests and weekly.
- Supply chain: every `uses:` is pinned to a commit SHA with a `# vX.Y.Z` comment, bumped by `.github/dependabot.yml` (Actions and the `pob_cli` uv lockfile). CI and release install from `pob_cli/uv.lock` with the interpreter from `setup-python` (`UV_PYTHON_DOWNLOADS=never`); builds run Python 3.14. Workflows default to `contents: read`. Vulnerability reports go through `SECURITY.md` (GitHub private reporting).
